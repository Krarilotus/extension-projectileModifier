# Native target selection: correction to the 1.8.10 prototype

Reference: original normal Crusader 1.41, `C:/UCPTools/Original-SHC141/Stronghold Crusader.exe`; OpenSHC's `UnitsState::acquireShootTarget` declaration and Ghidra decompilation checked against instructions at `0x54B0D0`–`0x54BDF7`. These reference addresses are **not runtime bindings**.

The game has a substantial automatic target policy in `UnitsState::acquireShootTarget`. For native shooters, it walks a per-player candidate list, excludes invalid or inappropriate entities, checks range, computes a base distance as `max(abs(dx), abs(dy))`, adds `50 * target.field265_0x3dc` (an attention counter whose exact meaning still needs confirmation), applies unit-type and shooter-mode-specific transformations, checks line of sight, and tracks both best overall and best unengaged candidates. It may prefer an unengaged target whose score is within 1.5 times the best score. Its final selection updates native target and attention state. Distance, target class, shooter class, attention, range, obstruction and candidate order all matter. A unit-type rank ordered before distance is not a faithful extension of this policy.

The native switch selects mode 2 for Catapult (unit type 39) and mode 3 for Trebuchet (40). Without a supported explicit order, both return before the automatic candidate loop (`0x54B796`–`0x54B7A8` in this reference image). This is deliberate native behavior. The module's configured `interval` and `targets` options use a separate `pickTarget`/`scanUnit` route to provide autonomous artillery and units which lacked it. That route currently scans all unit slots and picks the nearest eligible unit; it is an existing module design/performance concern, not evidence that the game lacks a richer owner. `targets: cluster` and automatic buildings/walls are deliberate module policies and should not silently inherit native unit acquisition rules.

The candidate-list producer at reference `0x532BA0` is called by the map's scheduled update from `0x45CA44`, `0x45CAC7`, `0x45CB51` and `0x45CBC9`. It scans living units for a player, records enemy unit IDs and native identity values up to a 2500-entry cap, and uses the game's RNG only on overflow. This list is refreshed by the game's schedule, not on every individual shot. Reusing it may remove the module's repeated full-unit scan, but changing from fresh to scheduled eligibility is an observable choice requiring gameplay and replay tests. Copying the list builder would duplicate the native owner.

The scorer instruction sequence at normal reference `0x54B9A8` and Extreme 1.41 reference `0x54BDC8` is byte-identical through the base distance/attention addition and shooter-mode branch. The Catapult/Trebuchet early-return sequence likewise matches at normal `0x54B792` and Extreme `0x54BBB2`. These are two verified research fixtures, not proof of all UCP-supported versions or safe hook ABI. No production hook was added.

OpenSHC's `PathFindingState::findDistanceOrThreatLevelToUnitUnk` is another distance-plus-type routine. Ghidra finds calls from an AI path at `0x51D54B` and `0x51D577`; it traverses map tiles and returns a unit based on path distance plus a type-specific term. It is **not** the general ranged acquisition path. `UnitsState::findClosestEnemyByAreaAndRange` likewise has an AI-area caller and its own score, but is not a general read-only priority API. This corrects the earlier audit's overbroad claim that no native threat-priority system existed.

The 1.8.10 `threat_priority` prototype applied a lexicographic rank only in the module's `scanUnit` and only for profiles with `interval`. It could select a distant ranked candidate regardless of the native score, and did not configure ordinary native acquisition. It has been reverted. The 1.8.10 tester package is superseded for this feature; 1.8.9 remains the existing automatic-search baseline while the native design is verified.

## Integration boundary for a corrected option

1. Trace the per-player candidate-list producer and eligibility/visibility lifecycle on normal and Extreme. Confirm the scorer and field meanings in both images, including existing module acquisition hooks.
2. Parameterize native scoring at its owner boundary, preserving distance, target-type transforms, range, line of sight, attention update and selection order. A per-shooter/per-target distance-equivalent adjustment is more meaningful than an absolute rank; omission must execute the original instructions and produce the same result and RNG order. Do not replace native candidate enumeration or add a second world scan.
3. For configured autonomous artillery, test whether the native candidate loop can safely be used at the module's scheduled shot boundary. Do not bypass native Catapult/Trebuchet early returns globally. Preserve manual/cow orders, animations, aim, release, ownership and native projectile allocation. If native acquisition cannot safely support this, retain an explicitly scoped module policy and do not call it native priority.
4. Resolve necessary hook sites with existing `core.AOBScan`/verified-context resolution, not these reference addresses. Check displaced instructions, branches, ABI and occupied hooks; verify normal/Extreme and applicable UCP-supported variants. Test deterministic target decisions and RNG, save/reload, paired multiplayer and crowded-map cost before a Store candidate.

The module's existing `templates.profile_code` is **not a pure profile lookup**: on a profile change it clears pending volley and synchronization state. A native scorer hook that calls it for each candidate could alter unrelated firing state. Split the read-only effective-profile lookup from that established side-effect owner, reuse the same lookup in both paths, and leave the state transition at its existing tick boundary. This is a prerequisite for per-unit/fortification/decoration target adjustments, not a reason to add a private scorer cache.

OpenSHC declarations expose reconstruction reference functions, not a shipped UCP runtime scorer API. UCP's existing AOB/assembly facilities can bind a minimal native hook if that owner boundary is proven. No new resolver, cache, scanner or target service is justified.
