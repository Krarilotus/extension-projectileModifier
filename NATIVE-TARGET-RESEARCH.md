# Native target selection: correction to the 1.8.10 prototype

Reference: original normal Crusader 1.41, `C:/UCPTools/Original-SHC141/Stronghold Crusader.exe`; OpenSHC's `UnitsState::acquireShootTarget` declaration and Ghidra decompilation checked against instructions at `0x54B0D0`–`0x54BDF7`. These reference addresses are **not runtime bindings**.

The game has a substantial automatic target policy in `UnitsState::acquireShootTarget`. For native shooters, it walks a per-player candidate list, excludes invalid or inappropriate entities, checks rounded-tile Euclidean range, computes a base distance as `max(abs(dx), abs(dy))` in eighth-tile coordinates, adds `50 * target.field265_0x3dc` (an attention counter whose exact meaning still needs confirmation), applies unit-type and shooter-mode-specific transformations, checks line of sight, and tracks both best overall and best unengaged candidates. It may prefer an unengaged target whose score is within 1.5 times the best score. Its final selection updates native target and attention state. Distance, target class, shooter class, attention, range, obstruction and candidate order all matter. A unit-type rank ordered before distance is not a faithful extension of this policy.

The native switch selects mode 2 for Catapult (unit type 39) and mode 3 for Trebuchet (40). Without a supported explicit order, both return before the automatic candidate loop (`0x54B796`–`0x54B7A8` in this reference image). This is deliberate native behavior. The module's configured `interval` and `targets` options use a separate `pickTarget`/`scanUnit` route to provide autonomous artillery and units which lacked it. That route currently scans all unit slots and picks the nearest eligible unit; it is an existing module design/performance concern, not evidence that the game lacks a richer owner. `targets: cluster` and automatic buildings/walls are deliberate module policies and should not silently inherit native unit acquisition rules.

The candidate-list producer at reference `0x532BA0` is called by the map's scheduled update from `0x45CA44`, `0x45CAC7`, `0x45CB51` and `0x45CBC9`. It scans living units for a player, records enemy unit IDs and native identity values up to a 2500-entry cap, and uses the game's RNG only on overflow. This list is refreshed by the game's schedule, not on every individual shot. Reusing it may remove the module's repeated full-unit scan, but changing from fresh to scheduled eligibility is an observable choice requiring gameplay and replay tests. Copying the list builder would duplicate the native owner.

The scorer instruction sequence at normal reference `0x54B9A8` and Extreme 1.41 reference `0x54BDC8` is byte-identical through the base distance/attention addition and shooter-mode branch. The Catapult/Trebuchet early-return sequence likewise matches at normal `0x54B792` and Extreme `0x54BBB2`. The range-table load and per-candidate rounded-range branch also share instruction contexts. These are two verified research fixtures, not proof of other builds.

OpenSHC's `PathFindingState::findDistanceOrThreatLevelToUnitUnk` is another distance-plus-type routine. Ghidra finds calls from an AI path at `0x51D54B` and `0x51D577`; it traverses map tiles and returns a unit based on path distance plus a type-specific term. It is **not** the general ranged acquisition path. `UnitsState::findClosestEnemyByAreaAndRange` likewise has an AI-area caller and its own score, but is not a general read-only priority API. This corrects the earlier audit's overbroad claim that no native threat-priority system existed.

The 1.8.10 `threat_priority` prototype applied a lexicographic rank only in the module's `scanUnit` and only for profiles with `interval`. It could select a distant ranked candidate regardless of the native score, and did not configure ordinary native acquisition. That path has been removed. The 1.8.10 tester package is superseded; the unreleased correction now biases the native scorer and uses its candidate list for configured non-random unit shots.

## Correction and owner bindings

| Capability | Owner and reuse decision |
|---|---|
| Candidate enumeration, eligibility, score transforms, LOS, attention and chosen-target state | Native `UnitsState::acquireShootTarget`; called once for configured non-random unit shots with an opt-in bonus. No copied candidate producer/scorer or extra world scan. Existing ordinary native acquisition also sees the bonus when configured. |
| Target position, height and leading | Native `UnitsState::prepareProjectileTarget` after scheduled unit selection; no synthetic target coordinates. Projectile allocation, damage and cleanup remain in the existing native fire path. |
| Runtime discovery and patching | Installed UCP framework `core.AOBScan`, `scanForAOB`, `allocateAssembly` and `writeCode` at revision `02a7a6b`. The module's existing `resolve.locate` checks duplicate/missing signatures. New contexts decode the native range table and branch continuations; no reference VA enters production. |
| Effective wall/decoration profile | Existing `configuration.validate` merge, `profileIndex` and `DECORPROFILE`. The read-only profile path avoids changing firing state inside acquisition. A per-type presence byte skips profile work for unrelated native shooters. |

The score hook subtracts `8 * threat_priority[target type]` from the native distance-plus-attention term, floored at zero, before the game's later policy. The original Catapult/Trebuchet early return is bypassed only during this module's synchronous shot, identified by the shooter stride. That shot substitutes the configured range at the native range-table load and uses exact eighth-tile Euclidean candidate eligibility when `strict_range` is true. All other native acquisitions replay their original range load and comparison. Manual orders, cluster and random-volley paths keep their existing choices.

Normal and Extreme 1.41 x86 harness tests exercise selection, range, wall overrides, manual precedence and the original no-option path. Live GUI/gameplay, paired multiplayer/save-replay, crowded-map timing and other supported executable fixtures remain acceptance work before Store release.

OpenSHC declarations expose reconstruction reference functions, not a shipped UCP runtime scorer API. No new resolver, scanner or target service was introduced.
